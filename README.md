# Quantumberg Task Planning

Task, project & employee management system for **Quantumberg Technologies** (Bengaluru,
1–20 employees). React + TypeScript + Tailwind (Vite) frontend, Supabase backend with
**row-level security (RLS)** — every business rule lives in the database, not in the UI.

## Stack

| Layer     | Tech                                                                 |
| --------- | -------------------------------------------------------------------- |
| Frontend  | React 19, TypeScript, Tailwind CSS v4, React Router, Supabase JS     |
| Backend   | Supabase (Postgres, Auth, Storage) with RLS + database triggers      |
| Local dev | PGlite-backed Supabase-compatible shim (`server/`) on `localhost:54321` |

## Quick start (local)

```bash
npm install

# terminal 1 — local database (schema + seed data)
npm run dev:db:reset      # start PGlite backend, reset & reseed
# or: npm run dev:db      # start without resetting

# terminal 2 — frontend
npm run dev
```

Open http://localhost:5173 — the Vite proxy forwards `/auth/v1`, `/rest/v1`, `/rpc`
and `/storage/v1` to the local backend, so no env vars are needed for local work.

### Verify the backend

```bash
npm run dev:db:reset      # in one terminal (leave running)
npm run verify:foundation # in another — must report "73 passed, 0 failed"
```

## Environment variables

Copy `.env.example` to `.env` (git-ignored) and fill in values for a hosted deploy:

| Variable                 | Where used | Description                                                        |
| ------------------------ | ---------- | ------------------------------------------------------------------ |
| `VITE_SUPABASE_URL`      | frontend   | Supabase project URL. Empty/absent = local dev (Vite proxy).       |
| `VITE_SUPABASE_ANON_KEY`  | frontend   | Anon (publishable) key. Falls back to `local-anon-key` locally.    |
| `VITE_LOCAL_BACKEND_URL` | vite cfg   | Override the local backend target (default `http://localhost:54321`). |
| `SERVICE_ROLE_KEY`       | server     | Service-role key for the local shim **only**. Never shipped to the client. |

**Never** put the service-role key in any `VITE_*` variable or in frontend code.

## Architecture notes

- **RLS everywhere**: `supabase/migrations/` defines tables, helper functions
  (`app_task_visible`, `app_task_editable`, …) and policies. The UI never enforces
  permissions — a hand-crafted request is rejected by Postgres.
- **Visibility model**: employees see tasks they are assigned to, created, or review,
  plus every task in projects they belong to. Personal tasks (`project_id IS NULL`)
  are private — even the owner cannot open someone else's. Personal tasks can only be
  created for yourself.
- **Workload**: `estimated_hours × (1 − progress/100)` remaining for open tasks due
  within 7 days, against a 40 h/week capacity (amber > 80 %, red > 100 %).
- **Notifications** are generated by database triggers
  (`app_notify_task`, `app_notify_comment`) — assignment, reassignment, priority,
  blocked, awaiting approval, comments and @mentions — with per-user dedupe keys.
  Clients cannot insert notifications directly (no insert policy).
- **Recurrence**: completing a recurring task (`tasks.recurrence` jsonb) spawns the
  next occurrence in the database (`app_spawn_recurring_task`), keeping project,
  assignee, estimate and the recurrence rule.
- **Activity log** is append-only (no UPDATE/DELETE policies).
- **Deactivation** (`profiles.is_active = false`) blocks sign-in; task history is kept.
- Time zone: everything is stored as dates/`timestamptz` and displayed in
  **Asia/Kolkata**.

## Deployment (hosted Supabase)

1. Create a Supabase project; note the project URL and anon key.
2. Apply migrations in order (`supabase/migrations/*.sql`) via the SQL editor or
   `supabase db push` — they are idempotent and ordered by timestamp.
3. Run `supabase/seed.sql` once to load the demo users/projects/tasks
   (change the seed password before any real use).
4. Create auth users for each seeded email with password `Quantum@2026`
   (the seed inserts profiles; Auth users must match the emails).
5. Configure the frontend:
   ```bash
   cp .env.example .env
   # VITE_SUPABASE_URL=https://<project>.supabase.co
   # VITE_SUPABASE_ANON_KEY=<anon key>
   npm run build
   ```
6. Host `dist/` on any static host (Vercel, Netlify, S3+CloudFront). Set the same
   env vars at build time.
7. Smoke-test: `SUPABASE_URL=… SUPABASE_ANON_KEY=… npm run verify:foundation`
   — the suite runs against any PostgREST-compatible endpoint.

Local-only pieces (`server/`, `dev:db*`) are not needed on hosted deploys.
